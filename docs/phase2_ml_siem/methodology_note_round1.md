# Phase 2 — Methodology Note: First ML Run and Decision to Iterate

**Date:** 28 May 2026
**Author:** Yosif Karageorgiev
**Stage:** Phase 2 (ML-Enhanced SIEM) — first iteration

## Summary

The Phase 2 Isolation Forest detection model was implemented and tested
against two datasets: (1) the original Phase 1 8,636-event capture and
(2) a freshly-collected 1,847-event Round 2 capture under identical
conditions. In both cases the model produced 0% recall on attacker
windows. This document records why this result occurred, what it tells
us about the experimental setup, and the decision to iterate the data
collection methodology before reporting final Phase 2 results.

## Results of the first ML run

| Dataset | Total events | Feature windows | Attacker windows | True positives | Recall |
|---|---|---|---|---|---|
| Phase 1 (original) | 8,636 | 13 | 2 | 0 | 0% |
| Round 2 (re-run) | 1,847 | 4 | 2 | 0 | 0% |

## Root cause analysis

The Isolation Forest algorithm requires a representative sample of
"normal" behaviour to learn a meaningful boundary, against which
genuine anomalies can be identified. Both datasets failed to provide
this for two related reasons:

1. **Log-shipper noise dominated the capture.** Event ID 4703 ("a token
   right was adjusted"), generated by the Fluent Bit service process
   during routine log shipping, accounted for ~94% of Phase 1 events
   and ~76% of Round 2 events. These events carry no source IP and no
   authentication signal. After filtering, the security-relevant
   remainder is small.

2. **Limited diversity of benign activity.** No deliberate baseline
   activity was generated before the attacks ran. Genuine "normal"
   behaviour was therefore restricted to system housekeeping, scheduled
   tasks, and minor service activity — all originating from one or two
   hosts. After feature engineering (per-IP, per-2-minute windows), the
   datasets resolve to only 4–13 distinct feature rows, of which 2 are
   attacker windows. This is far below the volume of representative
   "normal" behaviour required for any unsupervised anomaly detector to
   draw a robust decision boundary.

## Why this is a meaningful finding rather than a failure

The current result honestly indicates that the methodology used to
generate Phase 1 data is well-suited to evaluating rule-based detection
(which only needs the attack signal itself) but insufficient to
fairly evaluate ML-based anomaly detection (which additionally needs a
characterised baseline). This is a known limitation of comparative SIEM
research and aligns with the observations of Sommer & Paxson (2010)
that ML-based intrusion detection requires substantially richer training
data than rule-based methods.

The 0% recall result is not the algorithm failing; it is the
experimental setup failing to give the algorithm a fair test. Repeating
the same approach with the same data shape will produce the same
result. Iteration is therefore required.

## Decision to iterate

Phase 2 Round 1 is preserved as documented evidence (this note, plus the
exported JSON file `phase2_export.json` and the ML output artefacts in
`docs/phase2_ml_siem/`). The headline Phase 2 result reported in the
dissertation will come from Round 2, which uses a revised data collection
methodology:

1. Reset OpenSearch to a clean state.
2. Generate a structured baseline of benign activity for ~60–90 minutes
   (interactive logons, file shares, scheduled tasks) before any attack
   runs. This produces a representative population of "normal" feature
   windows that the model can learn from.
3. Execute the same `attack.sh` workload as Phase 1, on top of the
   established baseline.
4. Export the resulting dataset and apply the same Isolation Forest model
   without further code changes.

This revised methodology isolates the experimental variable correctly:
both Phase 1 and Phase 2 will be evaluated against the same baseline-
plus-attacks dataset, with detection method as the only difference.

## Implications for the dissertation

This iteration is itself a research finding. The dissertation Discussion
chapter will note that:

- Rule-based and ML-based detection have different data requirements.
- Comparative studies that ignore this risk producing misleading
  headline metrics.
- The first iteration's 0% result, while not the reported final result,
  is preserved as evidence of the methodological correction made during
  the study.
